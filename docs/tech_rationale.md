# 技术选型理由（面试速查版）

> 本文档把项目里的关键设计决策整理成「问题 → 方案 → 效果」三段式，方便在面试或 GitHub 介绍时直接引用。

---

## 1. 为什么用 Supervisor-Worker 多 Agent 架构？

**问题**：单 Agent 同时处理政策问答、费用归集、风险扫描、工时填报时，工具越多，LLM 越容易选错工具或产生幻觉；且不同任务对提示词、安全策略的要求不同。

**方案**：
- 用 **LangGraph StateGraph** 实现一个 `Supervisor` 中枢节点，专门做路由决策（LLM 决策 + 关键词兜底 `_ROUTE_FALLBACKS` 双层保障）；
- 4 个专职 Worker（`policy_agent` / `expense_agent` / `risk_agent` / `fill_agent`）各自只暴露最相关的工具；
- Worker 与 Supervisor 之间通过 `Command(goto=...)` 协作，形成"调度 → 执行 → 再调度/结束"的闭环。

**效果**：
- 每个 Worker 的 system prompt 聚焦单一职责，工具误用率显著下降；
- 新增 Worker 只需在 `WORKER_NAMES` 和 `_ROUTE_FALLBACKS` 里注册，扩展成本低；
- 与业务对齐：政策问答（查知识库）、费用归集（8 类口径）、风险扫描（金四指标）、工时填报（录入）各管一段真实流程。

## 2. 为什么 RAG 要做 BM25 + 向量 + RRF + Rerank 混合检索？

**问题**：政策文档往往"关键词明确但表述正式"（如"加计扣除""辅助账""委托研发"），纯向量检索对专有名词和短查询的精确匹配不够稳定；纯 BM25 又无法处理同义改写和语义相关表达。

**方案**：
1. **BM25 稀疏检索**（jieba 分词）：对政策中的关键词（加计扣除、辅助账、备查资料、8 类费用等）做精确召回；
2. **bge-small-zh-v1.5 向量检索**：捕获语义相似但字面不同的表达（如"研发花的钱怎么抵税"→"加计扣除"）；
3. **RRF 融合（Reciprocal Rank Fusion, k=60）**：不用调权重，就能把两路排名的互补结果融合；
4. **bge-reranker-v2-m3 CrossEncoder 重排**：在融合后的候选上做精细语义打分，把最相关的片段排到 top-3。

**效果**：
- 在检索评测集上，Recall@3 从纯向量的 **72%** 提升到混合检索的 **88%**，纯 BM25 仅 **61%**；
- 两路召回互相补缺：BM25 保专有名词命中，向量保语义泛化，重排保 top 结果质量。

> 指标复现：`python eval/retrieval_eval.py` + `python eval/plot_retrieval_eval.py`

## 3. 为什么政策问答要加 grounding 门控 + CRAG？（防幻觉）

**问题**：政策问答最怕 LLM 编造——财务人员拿编造的加计扣除比例去申报，后果严重。知识库没有的内容，模型很容易一本正经地"补全"。

**方案**（四层防线）：
1. **相关性门控**（`_is_relevant`）：检索到的文档与问题做关键词覆盖度打分（jieba 分词 + 停用词过滤），低于阈值直接拒答"知识库未收录该内容"，绝不硬答；
2. **CRAG 重搜**（`_rewrite_query`）：检索不足时，剥离口语前缀改写查询再搜一次，提高召回；
3. **引用来源**：回答必须附知识库文件名 + 片段，可溯源；
4. **缓存准入**（`_cacheable`）：只有带"📖 引用来源"的答案才写入缓存，避免把幻觉答案缓存住。

**效果**：
- 无关问题（如问天气）100% 拒答，不编造；
- 相关问题的答案可溯源、可核验；
- 幻觉答案不会因为缓存被"固化"。

## 4. 为什么敏感查询要加 HITL（人工审核）？

**问题**：员工问"我的工资是多少"时，LLM 可能幻觉编造或泄露隐私；直接调用检索也存在个人数据授权风险。

**方案**：
- `rag_tool.py` 中定义敏感关键词（我的 / 个人 / 工资 / 薪资 / 薪酬）；
- 命中后把查询写入 SQLite 审核队列，状态为 `pending`；
- 管理员通过 `python hitl.py` 执行 `approve <id>` 后，同一语义问题再次提问即可命中已批准记录并消费；
- 未批准前直接返回审核提示，不调用检索、不生成答案。

**效果**：
- 形成"机器预审 + 人工放行"的安全闭环；
- 语义关键词分组匹配解决了 LLM 改写 query 导致精确匹配失败的问题。

## 5. 多轮对话为什么不把完整历史喂给 Worker？

**问题**：ReAct 型 Agent 看到历史里的错误回复、HITL 提示或上一轮答案后，容易"偷懒"——不再调用工具，而是直接照搬或道歉。

**方案**：
- `_make_worker_node` 中只把**当前轮次的最后一条用户消息**传给 Agent；
- 多轮记忆仍然由外层 StateGraph 的 `AsyncSqliteSaver` 持久化，Supervisor 据此做路由；
- Worker 只负责"回答当前问题"，不负责维护跨轮上下文。

**trade-off**：
- 好处：彻底消除了历史污染导致的工具漏调用、串台回答；
- 代价：像"明天呢"这类指代性 follow-up 需要额外的上下文压缩模块，当前版本尚未实现。

## 6. 为什么工具执行要包一层 Agent Harness？

**问题**：Agent 调用工具可能卡死（网络）、超时、重试无限循环、异常未捕获——生产环境最怕"不可控"。

**方案**（`harness.py`）：
- `guarded_tool`：统一包装所有 Worker 工具——超时（10s）/ 有限重试（2 次）/ 异常日志 / 耗时统计；
- `AgentLoopGuard`：最大轮次 + 最大工具调用数，配合 LangGraph 的 `recursion_limit` 双保险防死循环；
- 包装用 `tool.copy(update={"func": wrapped})` 保留参数 Schema，不破坏工具接口。

**效果**：
- 所有工具执行"有界、可靠、可观测"；
- 面试可直接讲：这是把 Agent 从"demo"推向"生产"的关键一层。

## 7. 为什么用 MCP 暴露能力？（标准化接入）

**问题**：Agent 的能力（费用归集、风险扫描、工时填报）如果只写在 Python 函数里，外部系统或其他 Agent 无法调用——每个系统都要重写一遍。

**方案**（`mcp_server.py`）：
- 用 FastMCP 把 4 个工具（费用归集 / 风险扫描 / 工时填报 / 费用条目）暴露为标准 **MCP 工具**（stdio 传输）；
- 任何支持 MCP 协议的客户端（Claude、Cursor、自研 Agent）都可以直接调用。

**效果**：
- 能力一次开发、到处可调——"Agent 能力标准化"；
- 跟上 2026-2027 年的行业方向：MCP 已成为 Agent 工具接入的事实标准。

## 8. 为什么数学工具用 AST 而不是 `eval()`？

**问题**：`eval()` 会把用户输入的字符串直接当 Python 代码执行，存在代码注入风险。

**方案**：
- 用 `ast.parse()` 解析表达式；
- 只允许 `Num`、`BinOp`、`UnaryOp`、加减乘除幂和括号等白名单节点；
- 任何非法节点直接拒绝执行。

**效果**：在支持常见数学运算的同时，杜绝了 `__import__('os').system(...)` 这类注入。

## 一句话总结

> 这个项目把"研发费用管理"拆成了 **Supervisor-Worker 多 Agent 协作**（4 个专职 Worker）+ **混合检索 RAG + grounding 防幻觉** + **HITL 人工审核** + **Agent Harness 可靠执行** + **MCP 标准化接入** 五层：既有业务价值，又覆盖了 Agent 生产化的关键工程问题。
