# 技术选型理由（面试速查版）

> 本文档把项目里的关键设计决策整理成「问题 → 方案 → 效果」三段式，方便在面试或 GitHub 介绍时直接引用。

---

## 1. 为什么用 Supervisor-Worker 多 Agent 架构？

**问题**：单 Agent 同时处理政策问答、天气、计算时，工具越多，LLM 越容易选错工具或产生幻觉；且不同任务对提示词、安全策略的要求不同。

**方案**：
- 用 **LangGraph StateGraph** 实现一个 `Supervisor` 中枢节点，专门做路由决策；
- 3 个专职 Worker（`rag_agent` / `weather_agent` / `math_agent`）各自只暴露最相关的工具；
- Worker 与 Supervisor 之间通过 `Command(goto=...)` 协作，形成"调度 → 执行 → 再调度/结束"的闭环。

**效果**：
- 路由准确率从单 Agent 的"靠 prompt 祈祷"提升到关键词兜底 + LLM 决策双层保障；
- 每个 Worker 的 system prompt 聚焦单一职责，减少了工具误用；
- 新增 Worker 只需在 `WORKER_NAMES` 和 `_ROUTE_FALLBACKS` 里注册，扩展成本低。

---

## 2. 为什么 RAG 要做 BM25 + 向量 + RRF + Rerank 混合检索？

**问题**：企业内部制度文档往往是"关键词明确但表述正式"（如"婚假""差旅住宿标准"），纯向量检索对专有名词和短查询的精确匹配不够稳定；纯 BM25 又无法处理同义改写和语义相关表达。

**方案**：
1. **BM25 稀疏检索**（jieba 分词）：对制度中的关键词（年假、病假、公积金等）做精确召回；
2. **bge-small-zh-v1.5 向量检索**：捕获语义相似但字面不同的表达（如"怎么请假"→"休假流程"）；
3. **RRF 融合（Reciprocal Rank Fusion, k=60）**：不用调权重，就能把两路排名的互补结果融合；
4. **bge-reranker-v2-m3 CrossEncoder 重排**：在融合后的候选上做精细语义打分，把最相关的片段排到 top-3。

**效果**：
- 在 12 条员工高频咨询测试集上，Recall@3 从纯向量的 **72%** 提升到混合检索的 **88%**，纯 BM25 仅 **61%**；
- 两路召回互相补缺：BM25 保专有名词命中，向量保语义泛化，重排保 top 结果质量。

> 指标复现：`python eval/retrieval_eval.py` + `python eval/plot_retrieval_eval.py`

## 3. 为什么敏感查询要加 HITL（人工审核）？

**问题**：员工问"我的工资是多少""我的年假余额"时，LLM 可能幻觉编造或泄露隐私；直接调用检索也存在个人数据授权风险。

**方案**：
- `rag_tool.py` 中定义敏感关键词（我的 / 个人 / 工资 / 薪资 / 薪酬）；
- 命中后把查询写入 SQLite 审核队列（`approval.db`），状态为 `pending`；
- 管理员通过 `python hitl.py` 执行 `approve <id>` 后，同一语义问题再次提问即可命中已批准记录并消费；
- 未批准前直接返回审核提示，不调用检索、不生成答案。

**效果**：
- 形成"机器预审 + 人工放行"的安全闭环；
- 语义关键词分组匹配解决了 LLM 改写 query 导致精确匹配失败的问题（如"我的工资是多少"被改写成"工资薪酬制度"仍能命中）。

## 4. 多轮对话为什么不把完整历史喂给 Worker？

**问题**：ReAct 型 Agent 看到历史里的错误回复、HITL 提示或上一轮答案后，容易"偷懒"——不再调用工具，而是直接照搬或道歉。

**方案**：
- `_make_worker_node` 中只把**当前轮次的最后一条用户消息**传给 Agent；
- 多轮记忆仍然由外层 StateGraph 的 `AsyncSqliteSaver` 持久化，Supervisor 据此做路由；
- Worker 只负责"回答当前问题"，不负责维护跨轮上下文。

** trade-off**：
- 好处：彻底消除了历史污染导致的工具漏调用、串台回答；
- 代价：像"明天呢"这类指代性 follow-up 需要额外的上下文压缩模块，当前版本尚未实现。

## 5. 为什么数学工具用 AST 而不是 `eval()`？

**问题**：`eval()` 会把用户输入的字符串直接当 Python 代码执行，存在代码注入风险。

**方案**：
- 用 `ast.parse()` 解析表达式；
- 只允许 `Num`、`BinOp`、`UnaryOp`、加减乘除幂和括号等白名单节点；
- 任何非法节点直接拒绝执行。

**效果**：在支持常见数学运算的同时，杜绝了 `__import__('os').system(...)` 这类注入。

---

## 一句话总结

> 这个项目把"企业行政问答"拆成了 **Supervisor-Worker 多 Agent 协作** + **BM25/向量混合检索** + **HITL 安全审核** 三层，既提升了路由和检索的准确率，又用人工审核兜底了敏感查询风险。
